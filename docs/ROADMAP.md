# 路线图 Roadmap

本文档按阶段拆解 `quant-research` 的建设路径。每个阶段包含**目标、任务清单、完成标准（DoD）**。

最后更新：v0.1.0

---

## 目标与边界

**目标**：建成一套**可复现、可评估、防过拟合**的量化研究框架——输入是数据与策略想法，输出是可信的绩效结论。

**边界（明确不做）**：

- 实盘下单、券商 API、自动交易
- 实时行情接入、Tick 级 / 高频策略
- 任何形式的托管或生产环境部署

项目长期保持「离线研究 + 纸面验证」的定位，与 README 中的声明一致。

---

## 现状盘点

已完成的基础（v0.2.0）：

- ✅ src-layout 打包结构（`pyproject.toml` + setuptools）
- ✅ `pytest`、`ruff`、`mypy`（渐进式）、CI 与 pre-commit
- ✅ 数据 → 信号 → 仓位 → 含成本回测 → 指标表的最小闭环
- ✅ `shares` / `weights` 双账本交叉校验，零成本下逐点一致
- ✅ 69 条测试，覆盖校验、契约、账本、成本与时序
- ✅ 中文 README 与研究约定

已知缺口（按严重度排序）：

1. **横截面能力几乎空白**——无因子库、去极值/中性化预处理，也无 IC / IR 与分层回测。
2. **无实验归档**——参数、结果、数据指纹与代码版本仍靠手工记录，`reports/` 为空。
3. **样本外与稳健性流程未建立**——无 walk-forward、参数敏感性分析与滚动指标。
4. **数据工程仍有缺口**——派生缓存、跨标的日历对齐、上市首日与停牌处理尚未完成
   （原始数据的每日采集与 Parquet 落盘已具备）。
5. **组合约束不完整**——无行业 / 板块暴露上限与容量约束。
6. **工作台只剩认证缺口**——任务、采集、实验台账、参数网格都已有历史与对照，
   无认证（详见 [UI_DESIGN.md](UI_DESIGN.md) 的取舍与演进路径）。

## P8 — 尾盘选股流水线

**目标**：把「收盘后自动收数 → 全市场批量打分 → 给出可执行的选股建议」串成一条命令可跑通的
流水线，并让每一份建议都能被事后复盘。

产出定位：**研究性质的候选清单**，不是投资建议，也不接实盘——与开头的边界声明一致。

### 流水线

```
T 日 18:30  ─ ① 收数：当日全市场增量 → data/raw/<provider>/daily
            ─ ② 建板：增量拼宽表 → data/cache/<provider>_<adjust>.parquet
            ─ ③ 打分：向量化截面因子 → score(date × symbol)
            ─ ④ 选股：过滤(停牌/新股/流动性/一字板) → 排名 → Top N → target_weights
            ─ ⑤ 归档：选股报告 + 组合回测绩效 → 台账（含 as_of，供复盘）
            ─ ⑥ 界面：今日建议表（T+1 开盘执行）+ 历史建议复盘
```

### 现状：可直接复用 / 必须新建

| 环节 | 可复用的轮子 | 缺什么 |
| --- | --- | --- |
| 收数 | `collect_once`（增量、`pause`、重试、`should_stop`）、全市场 `all_symbols` | 尾盘编排、当日数据就绪校验 |
| 加载 | `load_price_panel` → `PricePanel`（宽表 date × symbol） | 全市场无缓存，每次重读上千个 Parquet |
| 打分 | `get_signal` + `STRATEGY_REGISTRY` | **只有 `ma_cross`(0/1) 与 `random`**，无连续分、无截面排名 |
| 组合 | `signal_to_weights`（`equal_weight` / `inverse_volatility`） | 无 Top N 截断入口 |
| 回测 | `run_backtest(weights)` | 无 signal-only 入口（两行可拼：`get_signal(...)` + `signal_to_weights(...)`） |
| 调度 | `run_daily_loop`（`--daemon --at`） | 无 `screen` 任务、无选股台账 |
| 排名 | `grid.rank` + `experiments.sort_key` | 只服务回测 row，非选股场景 |

三个决定设计方向的事实：

1. **现有信号是 0/1 宽表**（`index=DatetimeIndex`、`columns=标的代码`，无 `target_weights` 列）。
   `ma_cross` 在任一天会给几百只同时打 1，毫无区分度——选股要可用，必须先有**连续分**。
2. **`signal_to_weights(method="equal_weight")` 天然就是「当日得分为正者等权」**，正好是
   Top N 组合的现成映射，不必自己写。
3. **只有 baostock 同时具备全市场 + 免费 + 含 `amount`/`volume`**（另有 open/high/low/pctChg），
   是这条路唯一的主数据源。

### 任务清单

- [x] **S1 宽表缓存**：`data/cache/<provider>_<adjust>.parquet`（`data/cache.py`），按天增量更新、
      重复运行幂等；选股链路改读 `load_panel_cache()`，`load_price_panel` 保持原样
      （实测 30 只 × 683 日：逐文件 0.07s → 缓存 0.01s，规模上去后差距才明显）
- [x] **S2 尾盘编排**：`quant-nightly` 命令（`nightly.py`）串起「等到点 → 收数 → 增量刷新缓存
      → 打分 → 归档」。核心是**收数后先确认目标交易日真的在数据里**，不在就明确拒绝打分
      并写明最新到哪天——带着半天的数据打分，产出的名单看起来完整、实际是错的，
      而且会写进台账拖累几个月的复盘数字。实测（周一上午跑）：
      「2026-11-02 has not landed yet (latest is 2026-10-30); refusing to screen」
- [x] **S3 截面打分层**（新建 `src/quant_research/scoring/`）：动量（可跳过最近几日）、均线距离、
      波动率倒数、流动性等因子，各因子**逐日 z-score** 后加权合成
- [x] **S4 选股与可执行性过滤**：上市不足 N 日、流动性不足、**一字板不可成交**
      （`open == high == low` 且涨幅近停板）→ 剔除；只保留跑赢当日截面均值的标的
      （宁可少给几只，不为了凑数买「最不难看的输家」）→ `signal_to_weights`
- [x] **S5 归档与复盘**：`scoring/ledger.py` 按天归档（同一天重复运行覆盖而非追加——
      一天只有一份意见，两份只会让人分不清该信哪份）；`review()` 按「次日开盘买入、
      持有 N 个交易日卖出」回放历史名单，与回测的成交假设一致；窗口未走完的记录
      不参与统计。`quant-screen --review` 查看，样本只有几次时别当结论
- [x] **S6 界面与任务**：Web 新增「建议」视图（`GET /screen/latest`、`GET /screen/review`、
      `POST /jobs/screen`）。`schemas.py` 的 `JobOut.kind` Literal 已同步加 `"screen"`——
      漏了这一处，前端就收不到这类任务。名单卡同时写**名单日期**与**数据截至日**：
      没有日期的名单最容易被误读，盘前打开时它讲的是昨天，界面必须说清楚

### 必须一开始钉死的约束

1. **禁止前视**：信号用 T 日收盘数据，执行假定在 **T+1 开盘**（`ExecutionConfig(lag=1)`，
   引擎已强制，别关掉）。截面标准化必须**逐日**去均值，全样本一次性 z-score 会引入前视偏差。
2. **单 provider + 单 adjust**：不同源的前复权基准不同，跨源混用会让截面比较失去意义；
   缓存 key 必须带 `provider` 与 `adjust`。
3. **幸存者偏差**：样本只有当日仍在市的标的，退市股不在其中，回测出的组合收益天然偏乐观——
   建议单只能当筛选工具，文档里要写明。

### 已知坑（写在这里避免重复踩）

- `load_price_panel` 的 `missing_policy` 默认是 `"raise"`，全市场必然有停牌 NaN 会直接崩，
  **必须传 `"keep"`**。
- **`describe_panel` 不要在全市场跑**：跳变检测是 DataFrame 双层 `iterrows`，
  上千列 × 数千日会把这一步拖到分钟级。
- **当日数据不是 15:00 就有**：baostock 当日行情要盘后处理完才齐，现有默认
  `schedule_at: "18:30"` 已踩准，不要提前。
- **不要「逐只跑回测」**：那是上千次 `run_backtest`。打分向量化做一次，组合绩效再整体跑一次。
- 新增 `screen` 配置段时须同步 `config.py` 的字段白名单元组，未知键会直接抛错。
- 因子计算优先用 pandas `rolling`，**不引入 TA-Lib**（避免编译依赖）。

### 最小可跑闭环（建议先做这个）

不先做多因子框架，先把链路打通：

```
baostock 收数 → 单一动量因子(60 日收益) → Top 20 等权 → T+1 执行 → 出建议报告
```

跑通后再迭代：加因子、换 `inverse_volatility`、接界面。

**DoD**：一条命令完成「收数 → 打分 → 选股」，产出带 `as_of` 的建议单；用截断到 T-1 的
数据重算结果与原结果一致（防前视自检通过）；全市场一轮耗时可接受（分钟级，非小时级）。

## P9 — 因子检验

**目标**：给"加一个因子"这件事一把尺子。没有它，加任何新数据源都无法判断有没有用，
只能凭感觉说"名单看起来还行"。

- [x] **S1 诊断模块**（`scoring/diagnostics.py`）：
      `forward_return()`（**全项目唯一允许看未来的函数**，单独成文件，文件开头写明
      evaluation only）、`factor_ic()`（逐日截面秩相关）、`summarise_ic()`（t 值按重叠
      持有期 `÷√h` 打折）、`quantile_returns()`（分层收益 + 单调性）、`ic_decay()`
- [x] **S2 命令** `quant-factor --provider baostock --horizon 5 [--detail momentum]`；
      因子注册表与 `screen()` 共用一份定义，避免"因子"在两个地方含义不同
- [x] **S3 实测**：六个因子 × 678 个交易日，**无一条 `t(adj)` 超过 2**；
      `rsi_reversal` 方向为负且分层完全单调递减（反转假设在本样本不成立）；
      `inverse_volatility` IC 最高但分层不单调（关系非线性，线性加权消费不了它）。
      详见 [FACTORS.md](FACTORS.md)
- **明确不做**：不拿上面的数字反向调参数。那是用样本内结果过拟合，
  换个区间就会反过来打脸；要验证改动，只能看改动之后新积累的样本

## P10 — 财报风险

**目标**：给选股加一道价格看不见的否决权。七个因子全部来自价格，它们能说明别人在买
什么，不能说明这家公司靠什么活着。

- [x] **S1 拉取**（`fundamentals/fetch.py`）：BaoStock 四张季度表（盈利/偿债/现金流/
      成长）合并成宽表，按 `(symbol, period)` 一行；保留 `pubDate`
- [x] **S2 判定**（`fundamentals/risk.py`）：六面红旗（亏损 30、高杠杆 25、利润不含现金 20、
      短期偿债 15、净利腰斩 15、利息保障 10），分数 → 高/中/低/未知
- [x] **S3 命令** `quant-fundamentals [--as-of D] [--min-level 中] [--refresh]`
- [x] **S4 接入选股** `quant-screen --exclude-risky [中]`，剔除结果进 `dropped["financial_risk"]`
- [x] **S5 实测**：见 [FUNDAMENTALS.md](FUNDAMENTALS.md)——茅台负债 11.9%、伊利流动比 0.59、
      兴业银行 91.3% 被金融口径豁免

三个必须一开始钉死的点：

1. **没有财报不是低风险。** 输出 `未知`，且默认不剔除——但界面必须说清"未知不等于通过"。
2. **数据会错。** `liabilityToAsset` 出现过一百倍偏差（2025Q2 茅台报 0.0015，权益乘数
   反推 0.1475）。两者差 10 个百分点以上时以反推值为准，否则高杠杆公司会显示成没有负债。
3. **银行的负债是原料不是风险。** 毛利率缺失 + 负债率 > 85% 才按金融口径豁免，
   且豁免项仍列出（`waived`），不静默删除。

**明确不做**：不接商誉、诉讼、股权质押、审计意见。它们往往比比率更早预警，但需要另一
类数据源与另一套规则；先用六面旗把明显的问题挡在门外。

## P11 — 监管事件

**目标**：把「正在被证监会立案调查」变成选股的硬否决。财务红旗是概率判断，可以给权重；
立案调查不是——再融资与重组会在调查期间全部停摆，价格却常常还没反应。

- [x] **S1 取数**（`fundamentals/regulatory.py`）：**证监会官网没有「立案调查」栏目**，
      「行政处罚」列表又由 JS 异步填充、静态页无条目。改走**巨潮资讯**（法定披露平台）
      的标题 + 日期检索：`立案` 记开启、`行政处罚决定书/终止调查/撤销立案` 记结束
- [x] **S2 状态推导**：最近一次立案之后没有结案、且距今不超过 `active_days`（默认 365）
      才算「调查中」。没有现成的「调查中名单」接口，状态只能这样算出来
- [x] **S3 两档**：本体（公司 / 控股股东 / 实际控制人）硬排除；一般股东、董监高、
      子公司只提醒不排除——209 条立案里只有 95 条是本体，一刀切会误伤一批正常公司
- [x] **S4 手工名单** `config/regulatory.yaml`：补检索窗口之外的历史悬案
- [x] **S5 接入**：`quant-fundamentals` 特别提醒置顶（两段）+ 表格「监管」列；
      `quant-screen` 默认剔除，`--allow-investigated` 放行
- [x] **S6 实测**：见 [REGULATORY.md](REGULATORY.md)——回看一年 1.9 秒，
      76 只本体调查中、8 只股东/高管被立案

四个必须钉死的点：

1. **窗口要一年，不是六十天。** 案子可能查很久，「立案调查进展」公告就是老案在报
   进展。窗口短了，最该排除的那批恰好是隐形的。一年 10 个请求、1.9 秒，付得起。
2. **关键词决定成败。** `调查` 不能用（`尽职调查` 满屏），只能认 `立案`；而 `立案`
   还会命中法院的 `立案受理`／`受理立案`（词序会反）、公安的 `立案侦查`、纪检的
   `立案审查`。一年 368 条命中里真立案只占约四分之一。
3. **结案要分监管机构。** 财政部、税务局的《行政处罚决定书》不是证监会结案。
   把后者当成结案，等于给仍在被调查的公司开一张干净证明。
4. **静默失效最坏。** 从没检索过时选股会打警告，而不是悄悄放行——一个看起来生效、
   实际什么都没挡的过滤器，比没有过滤器更危险。

**明确不做**：不做语义理解。标题写「重大事项」正文才提立案的抓不到；规则是字面匹配，
边界写进文档而不是靠猜。

## 建议执行顺序

**P0 → P1 → P4 → P5 → P2/P3 → P6 → P7**

优先打通「数据 → 回测 → 绩效」这条最小闭环，再横向扩充策略库。
这样每新增一个策略都能立刻得到量化评估，避免在信号层堆积却没有衡量标准。

P8（尾盘选股流水线）依赖 P1 数据层、P2 信号层与 P4 回测引擎，建议在 P5 之后启动；
内部顺序按 S1 → S2 → S3 → S4 → S5 → S6，每步可独立验证，不存在「做完一半没法测」的情况。
